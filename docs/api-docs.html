API Docs

Build on Deep Safety with a stable modeling chain.

The API follows the physical workflow: materials and conditions feed scenario and source models, source models feed dispersion, and those outputs feed effects and hazard-evaluation workflows. Use the generated OpenAPI contract at /openapi.json and the endpoints below to integrate immediately.

HTTP runtime

Run the full OpenAPI-aligned FastAPI service with Docker or your own host.

Browser-local runtime

Use browser://local for the core interactive consequence workflow directly in GitHub Pages.

Agent surface

The MCP server and Python client expose the same contract for agent-driven and notebook-driven use.

Quick Start

Three ways to start using the API surface.

# Python package
pip install deepsafety

from deepsafety import DeepSafetyClient

client = DeepSafetyClient("http://127.0.0.1:8000")
materials = client.list_materials("ammonia")
scenario = client.select_release_scenario(
    {"scenarioType": "worst_case", "equipmentType": "pipe"}
)
// Browser-local runtime
const plume = await window.DeepSafetyBrowserApi.request(
  "POST",
  "/dispersion-models/solve",
  {
    model_type: "gaussian_puff",
    inputs: {
      released_mass_kg: 25,
      wind_speed_m_s: 3.0,
      stability_class: "D",
      x_m: 100,
      y_m: 0,
      z_m: 0
    }
  }
);
OpenAPI: fetch /openapi.json from the deployed service for code generation and downstream application contracts.

Model Chain

The API groups are intentionally upstream-to-downstream.

1. Materials: physical properties, toxicity, flammability, and reactivity starter data.
2. Scenario and source: realistic-case, worst-case, and conservative source-term calculations.
3. Dispersion and effects: concentration, radiation, blast, and human-impact calculations.
4. Hazard evaluation: HAZOP, FMEA, What-If, checklist, and input-validation workflows.

Foundational Inputs

These are the upstream data classes the API expects applications to manage explicitly.

  • Chemical physical properties, toxicity, flammability, and reactivity
  • Equipment geometry, inventory, and design data
  • Operating conditions such as temperature, pressure, and flow
  • Meteorology including wind speed, stability class, release height, and topography
  • Realistic, worst-case, and conservative scenario selections as first-class API choices
  • Starter registry files packaged separately from Python code for materials, toxic criteria, and constants

Endpoint Groups

These are the main families application developers usually wire first.

Family Representative endpoints Purpose
materials GET /materials, GET /materials/{materialId}/toxicity Foundational material data used by the rest of the modeling chain.
health POST /health/convert-concentration, POST /health/probit/evaluate Toxicology and industrial-hygiene utilities for exposure assessment.
scenario + source POST /scenario-engine/define, POST /source-models/gas-hole, POST /source-models/scenario/select Turn inventory, geometry, and failure mode into release rate, duration, and phase state.
dispersion POST /dispersion/gaussian-plume, POST /dispersion/dense-gas, POST /dispersion/isopleth Convert source terms into concentration fields, isopleths, and toxic-endpoint distances.
fire + explosion POST /fire-explosion/flammability/mixture, POST /fire-explosion/vce, POST /fire-explosion/bleve Translate flammable releases into ignition, blast, and BLEVE-style screening outputs.
prevention + relief POST /prevention/inerting/purge, POST /relief/system/analyze Evaluate purging, classification, fire protection, and relief-system decisions.
hazard evaluation POST /hazard-evaluation/hazop, POST /hazard-evaluation/fmea, POST /hazard-evaluation/what-if-checklist Use physical results in structured process-hazard-analysis workflows.

Physics Transparency

Deep Safety exposes equations and constants so applications can show the math, not hide it.

Gas release, choked flow
m_dot = C_d * A * P_0 * sqrt(
  k / (Z * R * T_0) * (2 / (k + 1))^((k + 1) / (k - 1))
)

Gaussian plume
C = Q_dot / (2 * pi * u * sigma_y * sigma_z)
  * exp(-y^2 / (2 * sigma_y^2))
  * [exp(-(z-H)^2 / (2 * sigma_z^2)) + exp(-(z+H)^2 / (2 * sigma_z^2))]

Thermal radiation
q = tau_a * chi_r * m_dot * DeltaH_c / (4 * pi * r^2)
  • shared.gravity_standard: gravitational acceleration driving hydrostatic liquid discharge.
  • shared.universal_gas_constant: links pressure, temperature, and molar volume in gas release calculations.
  • fire.default_radiative_fraction: fraction of combustion energy assumed to emerge as thermal radiation.
  • fire.default_atmospheric_transmissivity: fraction of thermal radiation assumed to survive the path to the receptor.

Scenario Example

A typical application flow from source selection to hazard study.

{
  "scenarioType": "worst_case",
  "equipmentType": "pipe",
  "inventoryMass": 1000,
  "siteTopography": "urban"
}
Step 1: call /source-models/scenario/select to make realistic or worst-case assumptions explicit.
Step 2: call a source route such as /source-models/gas-pipe or /source-models/flashing-liquid.
Step 3: feed the source output into /dispersion/* and then into /hazard-evaluation/*.

Runtime Notes

Choose the execution boundary that fits the application.

Browser-local: best for lightweight interactive screening, GitHub Pages demos, and embedded tools.
HTTP API: best for the full OpenAPI-aligned endpoint surface, shared services, notebooks, and production integrations.
MCP server: best when tools and agents need the same calculations through a standardized callable surface.
